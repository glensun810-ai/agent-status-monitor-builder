# 03 · 工程纪律与验证体系

> 这套系统能长期维护，靠的不是某个框架，而是下面这组「约束」。复刻时优先照搬纪律，再照搬代码。参考实现现役 **W29**（2026-11-16）。

## 一、十条硬纪律

1. **唯一真源**：所有源码、报告、验证只在一个根目录改；其它位置统称「镜像 / 注册点 / 归档」，不承载编辑。与记忆冲突时以磁盘实测为准。运行时事件流水也在真源目录之外。
2. **配置单点**：`paths.json` 管路径、`network.json` 管网络；页面里的常量块由脚本生成（BEGIN/END 标记），运行时展示值优先问 `/net`。禁止在 HTML 里散落字面量（静态展示文本除外）。
3. **单一同步通道**：真源 → 镜像 → 发布镜像 → 清单，只有 `sync_runtime.py --apply` 能做；`--sync-links` 是显式开关，先备份、逐文件 md5 校验；`--apply` 不重启进程、不改 plist，末尾自动跑预算自检。
4. **清单即事实**：`INVENTORY.json` 自动生成，新增 / 改动文件后先 `--apply` 再体检，否则「清单偏差」会判 FAIL。禁止手改清单。
5. **只读诊断，显式重建**：`health_check.py` 默认即 quick（**无 `--quick` 参数**，仅 `--full` / `--act` / `--strict`）只诊断；`--apply` 才重建；真实板子下发必须 `--act` 且需人工在场。
6. **改功能必补断言 + 留痕**：新增功能 → 补专项断言 → `--apply` → 一次全量复验；若导致 `CANON_BASELINE` 失配，重算并在 `VERSION.md` 留痕，**禁止静默更新**。仅删空白 / 注释不改基准值。
7. **基线不混增量**：老基线（504 项 = 450 + W19 54，自动命中 456 项）用于回归；新专项设 `bl=False` 独立判定（W29 专项 101 项）。老断言「全绿」不覆盖新功能，属「假绿」。
8. **断言必须校验真实对象**：配置 / 状态类断言不得只查源码字面量。参考 W29 A4-②：6 个 `dsSt*` elId 只在 `patchConfig` 里出现，DOM `[id^="dsSt"]` 实测只有 `dsStBright` ⇒ 两条只查字面量的 F 段断言是假绿。正确写法是正则提取全部 elId，逐个比对 DOM `id` 集合，任一悬空即 FAIL。
9. **体积护栏不放宽、按实测压缩上限报价**：护栏 200,000 B + `min_headroom_bytes` 4,000 B ⇒ 硬上限 196,000 B；W29 现役 195,966 B / 余量 4,034 B。理论空白量（曾估 8,180 B）不等于可释放量（实测 3,077 B）；压缩器须带 AST / 断言字面量保护，默认 dry-run、`--apply` 才写盘；压缩后全套 `verify_*.py` 复跑。
10. **现役真值表手工维护**：`sync_runtime.py` 源码 Grep `readme|现役|w29|baseline` 零命中 ⇒ **不会自动回写 README**。每次真值变动须手工同步 README 第五节，并在 `VERSION.md` 追加留痕。

## 三、环境分级（避免误报）

- **WARN（默认不影响退出码）**：板端断电 / 断网、Chrome CDP 未就绪、状态切换瞬时竞态（复跑通过）、固件版本断言在板端离线时、`/align` work 子态抖动。`--strict` 可收紧。
- **FAIL**：代码、配置、契约、清单、静态断言类失败，并打印明细。
- **复跑机制**：对齐 / 浏览器类失败后隔 2s 复跑一次，通过记 WARN 并留痕，仍失败才判 FAIL。
- **诚实口径**：取不到数据就显示未知 / 0，不用演示值；热力图标注真实覆盖天数与「演示数据」；人工验收项在输出中如实提示差额。

## 四、版本与文档惯例

- `VERSION.md` 用「版本 → 日期 → 关键决策 / 变更」表 + 每版小节；旧文原文不回改，冲突时追加「勘误」小节并注明「增量留痕，原文不回改」。
- 交付报告用 `vX.Y` + 勘误头；过期文档搬 `07-归档/`，不删史料。
- 文档口径统一到现役版本时，历史报告正文保留史实、只加勘误头。
- README 的「现役状态」表是唯一真值；编年史里的体积 / 按钮数 / 缓存名 / 基准哈希都是当时的中间值。**该表须手工维护**，同步脚本不代劳。
- 数据口径红线：`dur_s` 是相邻状态跃变间的任务周期（单条封顶 900s），≠ AI 有效思考时长 / 人工工时；不完整自然日不做同口径日环比；报告与视频均为静态快照。

## 五、一次改动的标准动作（按顺序）

1. 先跑 `python3 health_check.py`（只读），确认起始状态干净。
2. 只改必要的文件；配置类改动落在 `network.json` / `paths.json`。若页面接近硬上限，先算可用余量（现役仅 34 B），必要时先测实测安全压缩上限。
3. 补对应专项断言，命名 `verify_wXX.py`，并在体检中注册（`bl=False`）。断言须校验真实 DOM / 运行时对象，不写只查源码字面量的假绿断言。
4. `python3 sync_runtime.py --apply`：重建页面生成块 → 镜像 → 发布镜像 → INVENTORY → 预算自检。
5. 跑一次 `health_check.py --full`，确认 PASS / WARN / FAIL 与预期一致。
6. 涉及偏好、缓存、初始化顺序、SW 的改动，追加真浏览器「改值 → 刷新 → 回读」往返；涉及压缩的改动，复跑全部 `verify_*.py` 与三段内联 JS `node --check`。
7. 在 `VERSION.md` 追加决策留痕；若基准哈希失配，同时记录重算前后值。
8. **手工同步 README 现役真值表**（体积、按钮计数、SW 缓存、CANON、专项项数、复验结果）。
9. 明确列出「需人工在场项」，不替人签字。
